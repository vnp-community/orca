# Orca Frontend — Page Inventory

This directory documents every page in `frontend/` (the renderer app shared by the
Electron desktop build, the multi-user web server build, and the standalone admin
console). It was generated by reading the app's entry points and top-level view
switch, not by walking a conventional router — Orca doesn't use one for its main
app; it switches a single `activeView` field in the Zustand store instead.

- [`page-tree.md`](./page-tree.md) — hierarchical map of every entry point and page.
- [`pages/`](./pages/) — one file per page: what data it shows and how it's laid out.

## Three entry points

The renderer bundle boots into one of three completely separate top-level apps,
decided by `frontend/src/renderer/src/web/main.tsx` at load time:

1. **Desktop app** (`main.tsx`) — Electron renderer, pair-code/local single-user
   mode. Mounts the main `App` component directly.
2. **Multi-user web app** (`web/main-web-bootstrap.tsx`) — used when the server
   exposes `/auth/config` (`ORCA_MULTI_USER=1`). Shows `LoginPage` first, then the
   same main `App` component, wired to the browser's own authenticated session.
3. **Legacy pair-code web app** (`web/pair-code-app-entry.tsx`) — fallback when
   `/auth/config` 404s (an older single-user server). E2EE pairing UI instead of
   a login form, otherwise the same main `App`.
4. **Admin console** (`components/admin/AdminApp.tsx`) — a separate, small React
   app for server operators (user/session/policy/audit management). Not part of
   the main `App` — it's its own bundle entry.

## The main App's 9 top-level views

Once inside the main `App` (`frontend/src/renderer/src/App.tsx`), navigation is a
single `activeView: TopLevelView` field in the UI store slice
(`frontend/src/renderer/src/store/slices/ui.ts`), switched via `setActiveView()`
from the left sidebar (`components/sidebar/SidebarNav.tsx`). Exactly one is
visible at a time; `App.tsx` renders each behind
`{activeView === '<name>' ? <Component /> : null}` inside a
`RecoverableRenderErrorBoundary` keyed `page.<name>`.

| `activeView` | Page | Component |
|---|---|---|
| `terminal` | [Workspace / Terminal](./pages/terminal.md) (default) | inline in `App.tsx` (`WorktreeCreationPanel` / `Landing` / sidebar+terminal+editor+agent layout) |
| `workspace` | [Project Workspace (Beta)](./pages/project-workspace.md) | `WorkspaceLayout` (+ `ProjectSwitcher`) |
| `settings` | [Settings](./pages/settings.md) | `Settings` |
| `tasks` | [Tasks](./pages/tasks.md) | `TaskPage` |
| `activity` | [Activity](./pages/activity.md) | `ActivityPrototypePage` |
| `automations` | [Automations](./pages/automations.md) | `AutomationsPage` |
| `space` | [Space (disk-usage manager)](./pages/space.md) | `WorkspaceSpacePage` |
| `skills` | [Skills](./pages/skills.md) | `SkillsPage` (fully wired, but no UI currently links to it — see the page doc) |
| `mobile` | [Mobile](./pages/mobile.md) | `MobilePage` |

doc rather than getting their own file.

## `Settings` is one page with many sections, not many pages

`Settings` is a single `activeView` with an internal, in-page section list (General,
Appearance, Terminal, Git, Shortcuts, Voice, Orchestration, Computer Use, MCP,
Sessions, …) driven by `useSettingsNavigationMetadata()` and a left-hand nav rather
than by `activeView`. [`pages/settings.md`](./pages/settings.md) documents the page
shell and lists every section; it doesn't split each section into its own file.
