# Tasks

**Route / trigger:** `activeView === 'tasks'` in the Zustand app store (`frontend/src/renderer/src/store/`). Reached via `openTaskPage(data?, options?)` / `setActiveView('tasks')` — clicked from the sidebar's "Tasks" nav button, or opened with a preselected repo/provider/work-item from elsewhere in the app (e.g. "view on GitHub/GitLab/Linear/Jira" affordances populate `taskPageData`).
**Top-level component:** `TaskPage` (default export) — `frontend/src/renderer/src/components/TaskPage.tsx:724` (~8,280 lines), lazy-loaded from `App.tsx` (`const TaskPage = lazy(() => import('./components/TaskPage'))`) and rendered when `activeView === 'tasks'` (`App.tsx:2455`).

## Purpose
A unified work-item board that aggregates issues/PRs/MRs from GitHub, GitLab, Linear, and Jira into one filterable, per-repo-scoped view, and lets a user turn any item into a new Orca workspace (worktree) with one click — bridging "here's what I need to work on" and "here's a terminal/agent session to work on it in."

## Layout
Single-column page (not split with the left worktree sidebar/right sidebar chrome — the right sidebar unmounts on this view) with a compact top chrome band and a scrollable list/table body below it. A work-item detail view can swap in over the list body.

```
┌───────────────────────────────────────────────────────────────────┐
│ [X close] [GH][GL][Lin][Jira] source icons   repo picker   scope   │  <- top chrome (hideable)
│ preset/filter row (per-source: GitHub modes, Linear views, …)      │
├───────────────────────────────────────────────────────────────────┤
│                                                                     │
│   list / table / board body, per active source                     │
│   (GitHubItemDialog / PullRequestPage swap in here when an          │
│    item is opened, replacing the list — not a modal overlay)        │
│                                                                     │
└───────────────────────────────────────────────────────────────────┘
```

- **Top chrome** — a close button (`closeTaskPage`), a row of per-provider icon toggle buttons built from `getSourceOptions()` (`components/task-page-localized-options.tsx`: `github`/`gitlab`/`linear`/`jira`, filtered to `visibleTaskProviders`), a repo/project multi-select (`TaskProjectSourceCombobox`, `components/task-project-source-combobox.tsx`) driving `repoSelection`, and provider-specific controls — e.g. `LinearScopeSelector` (workspace/team picker) when `taskSource === 'linear'`, GitHub mode buttons (Issues/PRs/Projects, from `getGitHubModeButtons()`), Jira preset chips (`getJiraPresets()`: Assigned/Reported/All Open/Done), GitLab issue/MR filters. This whole band can be hidden (`taskPageListChromeHidden`, via `shouldHideTaskPageListChrome` in `components/task-page-list-chrome-visibility.ts`) while a detail view (`dialogWorkItem`) is open.
- **Body** — provider-specific rendering: GitHub renders either a flat sortable table of issues/PRs (`githubMode === 'items'`) or a Kanban-like `ProjectViewWrapper` (`githubMode === 'project'`); Linear supports list vs. board view (`getLinearViewOptions()`) with grouping (`getLinearGroupOptions()`: none/status/assignee/priority/team) and ordering; Jira and GitLab render their own filtered lists. `TaskPageJiraSortControls` (`components/task-page-jira-sort-controls.tsx`) is one example of a source-specific sub-component pulled out of the main file.
- **Detail view** — opening an item does not open a modal; it swaps the whole body for a full-page detail component while the top chrome hides: `PullRequestPage` (`components/PullRequestPage.tsx`, ~7,370 lines) for GitHub PRs, or `GitHubItemDialog` (also in `components/`) for GitHub issues. See `<PullRequestPage>` at `TaskPage.tsx:4696`, gated by `taskSource === 'github' && dialogWorkItem && dialogWorkItem.type === 'pr'`; the sibling `GitHubItemDialog` branch handles `dialogWorkItem.type !== 'pr'`. Both receive `onClose={closeTaskDetailPage}` and `onUse={handleUseWorkItem}` (create-workspace action available from inside the detail view too).
- A "new workspace" composer (`GitHubMarkdownComposer`, `components/github/GitHubMarkdownComposer.tsx`) is also rendered from this page (around `TaskPage.tsx:6778`) for drafting a linked comment/PR reply.
- The file carries a project-sanctioned `max-lines` grandfathered exception (see Notable implementation details) — its own eslint-disable is baselined, not something new code should copy.

## Data shown
- **Provider connection/status**: `s.linearStatus`/`linearStatusChecked`/`linearStatusContextKey`, `s.jiraStatus`/`jiraStatusChecked`/`jiraStatusContextKey`, `s.preflightStatus`/`preflightStatusChecked` (drives `gh`/`glab` CLI install detection), all from Zustand slices reached via `useAppStore`. Each is validated against `providerRuntimeContextKey`/`expectedPreflightContextKey` so a stale status from a previous host/runtime doesn't render as current.
- **Repo/project scope**: `s.repos` filtered to `isGitRepoKind`, `s.settings.defaultRepoSelection` (persisted sticky selection), `pageData.preselectedRepoId` (from `openTaskPage()` caller). `repoSelection` (local `useState<ReadonlySet<string>>`) is the working selection, normalized via `normalizeTaskRepoSelection`/`getDefaultTaskRepoSelection`.
- **Provider visibility/defaults**: `s.settings.visibleTaskProviders` (which of github/gitlab/linear/jira show as icon toggles — `hideTaskSource()` writes this back), `s.settings.defaultTaskSource`, `s.settings.defaultTaskViewPreset` (seeds the initial GitHub query via `getTaskPresetQuery`).
- **Resume state**: `s.taskResumeState` / `setTaskResumeState()` (`store/slices/ui.ts`) — persists the last-used mode/preset/query per provider across page visits: `githubMode`, `githubItemsPreset` (validated against `VALID_TASK_PRESETS` = `all`/`issues`/`review`/`my-issues`/`my-prs`/`prs`), `githubItemsQuery`, `linearMode` (validated against `VALID_LINEAR_MODES` = `issues`/`projects`/`views`), `linearQuery`, `jiraPreset` (validated against `VALID_JIRA_PRESETS`), `jiraQuery`.
- **Work items themselves**: fetched per-provider — GitHub `GitHubWorkItem[]`, GitLab `GitLabWorkItem[]`, Linear `LinearIssue[]`, Jira `JiraIssue[]` (types from `frontend/src/shared/types.ts` / `gitlab-types.ts`) — scoped by `TaskSourceContext` (provider + projectId + hostId + providerIdentity), built per repo via `getTaskPageRepoSourceContext(repo, provider)`. Multi-host execution is supported: `hostRegistryById` (built from `buildExecutionHostRegistry`) maps each repo/context to its execution host (local, SSH, or a paired runtime environment), and runtime-hosted GitHub/GitLab preflight checks run per host (`runtimePreflightStatusByHostId`, via `callRuntimeRpc(..., 'preflight.check', ...)`).
- **Detail view target**: `dialogWorkItem` (local state) plus `dialogInitialTab`, `dialogRepoPath`, `dialogSourceContext` — populated when a row is clicked, or pre-seeded from `pageData.openGitHubWorkItem`/`openGitLabWorkItem`/`openLinearIssue`/`openJiraIssue` when `openTaskPage()` was called with a specific item to jump straight to.
- **Attached-workspace lookups**: `findGithubWorkItemWorkspaceAttachment(allWorktrees(), repoId, type, number)` checks whether a work item already has a worktree/agent session tied to it, so clicking it can reveal the existing workspace instead of creating a duplicate.

## Key interactions
- Click a provider icon (GitHub/GitLab/Linear/Jira) → `openTaskPage({ taskSource }, { recordTasksInteraction: false })` switches the active source and persists it as `defaultTaskSource` via `updateSettings`.
- Click a work item row → opens the detail view (`dialogWorkItem` set); for GitHub PRs this mounts `PullRequestPage`, for issues `GitHubItemDialog`; `closeTaskDetailPage` returns to the list.
- "Use" / create-workspace action on an item (`handleUseWorkItem`) → `createGitHubWorkItemWorkspaceInBackground({ item, repoId, taskSourceContext, telemetrySource, openModalFallback })`: creates a new worktree/workspace in the background pre-linked to that issue/PR, falling back to opening the `new-workspace-composer` modal (`openComposerForItem` → `openModal('new-workspace-composer', { linkedWorkItem, taskSourceContext, prefilledName, initialRepoId, telemetrySource: 'sidebar' })`) when a background create isn't possible. Equivalent `openComposerForGitLabItem`/`openComposerForLinearItem`/`openComposerForJiraItem` helpers exist per provider.
- Click a work item that's already attached to a worktree (`handleOpenOrUseGitHubWorkItem`) → activates and reveals that existing worktree (`activateAndRevealWorktree`) instead of creating a new one.
- Repo/project multi-select (`TaskProjectSourceCombobox`) → narrows `repoSelection`, re-scoping which repos' items are fetched; selection auto-prunes when a previously-selected repo is removed and preserves "all selected" stickiness when the eligible repo set grows.
- Per-source filter/preset controls (GitHub Issues/PRs/Projects mode, Linear list/board + group-by/order-by, Jira Assigned/Reported/All Open/Done, GitLab issue/MR filters) → update `taskResumeState` so the choice survives navigating away and back.
- Hide a provider from the icon row (`hideTaskSource(provider, label)`) → removes it from `settings.visibleTaskProviders` (always keeps at least one visible; falls back to `github`) and reassigns `defaultTaskSource` if the hidden provider was the default.
- Linear: connect/switch workspace or add team access (`LinearScopeSelector`, `LinearApiKeyDialog`, `checkLinearConnection`). Jira: connect a site (`connectJira`, `selectJiraSite`, `checkJiraConnection`).

## Notable implementation details / known issues
- `TaskPage.tsx` carries a checked-in `/* eslint-disable max-lines */` at the top of the file — an intentional, baselined exception (see `config/max-lines-baseline.txt`, which also references it as the "grandfathered" home for several extracted-but-still-related helper modules like `task-page-github-status-actions.ts`). Per `AGENTS.md`, no *new* file should add its own max-lines disable outside that baseline process — this one predates the rule.
- The detail view is a full swap of the page body, not a modal/dialog overlay — `PullRequestPage`/`GitHubItemDialog` fully replace the list while `dialogWorkItem` is set, and the top filter chrome hides via `taskPageListChromeHidden`. This matters for anyone adding a "back" affordance: it must go through `closeTaskDetailPage`, not a generic dialog-close pattern.
- `PullRequestPage` (`components/PullRequestPage.tsx`) is itself a large, mostly self-contained page component (PR conversation/checks/files tabs) — it is not Tasks-specific; the same component is presumably reused elsewhere for PR detail rendering, so changes to it should be checked against other call sites, not just `TaskPage.tsx`.
- Work-item fetching is host-aware: GitHub/GitLab task sources can be backed by a local repo, an SSH host, or a remote-paired runtime environment, each with independent `gh`/`glab` auth and installation state (`preflightStatus` vs. `runtimePreflightStatusByHostId`). A repo whose execution host is unavailable/unauthenticated surfaces via `taskSourceAvailabilityNoticeByProvider` rather than silently returning no items.
- `taskResumeState` explicitly validates every field against a `VALID_*` allow-list (`VALID_TASK_PRESETS`, `VALID_LINEAR_PRESETS`, `VALID_LINEAR_MODES`, `VALID_JIRA_PRESETS` in `store/slices/ui.ts`) before trusting it — defends against corrupted/stale persisted UI state resurrecting an invalid preset id after a schema change.
