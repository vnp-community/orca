# Backend ↔ Agent — Connection Types &amp; Transport

This file catalogs every distinct way `backend/` (the Orca backend/gateway process)
and `agent/` (the dev-server agent that runs on a local or remote dev host) connect
to each other — transport, framing, handshake, auth, keepalive, reconnection. It was
generated by reading the current source directly (not existing design docs — several
files under `specs/agent/tdd/v5/` describe an earlier/narrower shape of this surface;
where they drift from the code, this doc follows the code and flags the drift in
[`gaps-and-findings.md`](./gaps-and-findings.md)).

See also: [`agent-rpc-catalog-git-fs.md`](./agent-rpc-catalog-git-fs.md) /
[`agent-rpc-catalog-runtime.md`](./agent-rpc-catalog-runtime.md) for what the agent
exposes for the backend to call over these connections, and
[`backend-rpc-catalog.md`](./backend-rpc-catalog.md) for the reverse direction.

## 0. Two protocol stacks, three connection modes

The repo contains **two separate wire protocols** that share a near-identical
13-byte frame header but are otherwise independent implementations, plus a third
connection type that's really a variant deployment of one of them:

- **Stack A — "Agent Wire Protocol v1"** (`agent/src/shared/agent-wire-protocol.ts`,
  `agent/src/relay/agent-wire.ts`): used only between `agent-entry.ts` (the agent
  process itself) and `AgentWebSocketServer` (backend) for the `direct-websocket`
  and `relay-websocket` modes. Single JSON-RPC channel, handshake method
  `agent.handshake`.
- **Stack B — "Relay protocol"** (`agent/src/relay/protocol.ts`,
  `agent/src/relay/dispatcher.ts` = `RelayDispatcher`, `agent/src/relay/relay-handshake.ts`):
  the SSH-exec-channel relay daemon protocol (`relay.js`, deployed standalone to
  the remote host), used for `relay-ssh` mode, multiplexed via
  `SshChannelMultiplexer` (`backend/src/main/ssh/ssh-channel-multiplexer.ts`).
  `backend/src/relay/protocol.ts` and `backend/src/relay/dispatcher.ts` are
  **verbatim mirrors** of the `agent/src/relay/` copies — but see the note in
  §4 below: this backend copy is vendored, not actually imported by
  `backend/src/main/**`.

**Important convergence**: `backend/src/main/dev-server/ws-handshake.ts:14-18`
imports `encodeJsonRpcFrame`/`FrameDecoder`/`MessageType` from
`../ssh/relay-protocol` — **Stack B's** framing/decoder — not from `agent-wire.ts`
(Stack A's codec). Both stacks use the same 13-byte header shape and the same
`MessageType.Regular=1`/`KeepAlive=9` values (Stack B additionally defines
`Handshake=2`), so once the `agent.handshake` JSON-RPC exchange completes, the
backend decodes a `direct-websocket`/`relay-websocket` agent connection with the
**same** `FrameDecoder`/`SshChannelMultiplexer` machinery it uses for `relay-ssh`
— via `createWebSocketTransport()` (`backend/src/main/dev-server/ws-transport.ts`),
which adapts a raw WS into `SshChannelMultiplexer`'s `MultiplexerTransport`
interface. In other words: all three connection modes converge on the same
multiplexed request/response engine after their (mode-specific) handshake.

Connection-mode literal type — `backend/src/shared/dev-server-types.ts:5-8`
(mirrored verbatim in `agent/src/shared/dev-server-types.ts:6-8`):

```ts
export type DevServerConnectionType =
  | 'relay-ssh'         // Orca SSH → deploy relay → stdin/stdout
  | 'relay-websocket'   // Dev server connects WS → Orca (reverse)
  | 'direct-websocket'  // Orca connects WS → dev server relay
```

`DevServerRelayBridge.connect()` throws for any other value
(`dev-server-relay-bridge.ts:203-206`).

## 1. `direct-websocket` — default, agent-initiated outbound

| | |
|---|---|
| Who initiates | The **agent** connects outbound to the Orca backend. Backend is the WS server. |
| Transport | `ws://<host>:<httpPort>/agent` — `AGENT_WS_PATH = '/agent'` (`agent/src/shared/agent-wire-protocol.ts:28`). Backend attaches via `AgentWebSocketServer.attach(httpServer)` intercepting HTTP `upgrade` for that exact path (`backend/src/main/dev-server/agent-ws-server.ts:59-72`), wired at `backend/src/server/index.ts:106`. |
| Default agent URL | `ORCA_URL = 'wss://<gateway-host>/agent'` (`agent/src/relay/agent-config.ts:86`) |
| Auth | One-time (or renewable) bearer token, `AGENT_TOKEN`, sent inside the `agent.handshake` params (field `agentToken`, only included when set — `agent-session.ts:206`). Backend validates by pre-registered "slot": `AgentWebSocketServer.registerSlot(agentToken, onConnected, onExpired)` (`agent-ws-server.ts:85-111`) stores `SHA-256(agentToken)` as the map key (`agent-ws-server.ts:93,237-239`) — never plaintext. `runOrcaReceiverHandshake`'s `validateToken` checks `pendingSlots.has(hashToken(token))` (`agent-ws-server.ts:139-147`). Slot auto-expires after `AGENT_CONNECT_TIMEOUT_MS = 60_000`ms. |
| Agent impl | `agent/src/relay/agent-connection-direct.ts` — `connectDirect()`, `new WebSocket(config.orcaUrl, {...})` (line 101). |
| Backend impl | `AgentWebSocketServer.handleConnection` (`agent-ws-server.ts:121-219`) → `runOrcaReceiverHandshake` (`ws-handshake.ts:156-311`) → on success, wraps the raw WS in `createWebSocketTransport(ws)` + `new SshChannelMultiplexer(transport, ...)` (`agent-ws-server.ts:198-201`) and invokes the slot's `onConnected(mux, info)` — either `DevServerRelayBridge.connectDirectWebSocket`'s inline handler (`dev-server-relay-bridge.ts:257-331`) or `connectWithExternalToken` (`:345-406`, used by the daemon/systemd flow via `POST /api/agent-token`). |
| When used | **Default mode** (`agent-config.ts:75`: `MODE` env defaults to `'direct-websocket'`). For dev servers behind NAT/firewall that can dial out. Agent auto-reconnects; typically run under systemd so the whole process restarts with a fresh token on unrecoverable failures. |
| Token single-use | The backend's `registerSlot` is consumed (`removeSlotByHash`) the moment a connection successfully handshakes (`agent-ws-server.ts:160-161`) — by design single-use. The agent's reconnect path always forces a fresh `tokenManager.forceRenew()` before retrying (`agent-connection-direct.ts:232-243`). |

## 2. `relay-websocket` — backend-initiated inbound, agent listens

| | |
|---|---|
| Who initiates | The **backend (Orca)** connects outbound to the agent, which runs its own `WebSocketServer`. |
| Transport | `ws://<devServerHost>:<agentPort>/orca-relay` (path literal `'/orca-relay'`, `agent-connection-relay.ts:45`). Agent's `AGENT_PORT` env, default `6799` (`agent-config.ts:97`). |
| Auth | Long-lived shared secret `ORCA_AGENT_TOKEN`, **mandatory** — "no fallback to insecure 'relay-secret'" (`agent-connection-relay.ts:32-42`). Accepted via `?token=` query param **or** `Authorization: Bearer <token>` header (`agent-connection-relay.ts:96-129`, `authenticate()`). Rejects with WS close code 1008 on mismatch. Never expires or rotates on its own (contrast with `direct-websocket`'s `AgentTokenManager`). |
| Agent impl | `agent/src/relay/agent-connection-relay.ts` — `listenRelay()`, `new WebSocketServer({ port: config.agentPort, path: '/orca-relay' })`. |
| Backend impl | `DevServerRelayBridge.connectRelayWebSocket()` (`dev-server-relay-bridge.ts:420-551`). Strips `?token=` from the configured `wsUrl`, sends it as an `Authorization: Bearer <token>` header instead (lines 424-445), runs `runOrcaInitiatorHandshake(ws, orcaVersion)` (`ws-handshake.ts:56-138`) — **Orca sends the `agent.handshake` request itself** (`{method:'agent.handshake', params:{orcaVersion}}`, seq=1/ack=0) and waits for the agent's `result`. On success, wraps in `SshChannelMultiplexer` same as direct mode. Owns its own reconnect loop (backend, not agent, owns reconnection here) with exponential backoff (`calcBackoffDelay`, `:46-54`: base 2s, max 60s, ±1s jitter). |
| When used | Agent behind NAT/firewall that Orca cannot reach outbound-only is irrelevant here — rather, used when the agent is reachable at a known LAN/VPN address but *cannot* dial out to Orca. No auto-reconnect on `dev-server-manager` restore (comment `dev-server-manager.ts:65`). |

## 3. `relay-ssh` — legacy/original mode, SSH exec channel

| | |
|---|---|
| Who initiates | The **backend**, over an already-established SSH connection (`SshConnectionManager`), deploys and launches `relay.js` on the remote host, then talks JSON-RPC over the SSH exec channel's stdin/stdout. |
| Transport | **Not a WebSocket at all** — an SSH `exec` channel. The relay daemon reads/writes framed bytes over its own stdin/stdout, tunneled through the SSH session, multiplexed client-side by `SshChannelMultiplexer`. |
| Auth | Implicit — trust boundary is the SSH connection itself (`sshTargetId` must already be connected, `dev-server-relay-bridge.ts:140-154`). No separate agent token. There is a wire-level **version** handshake (`relay-handshake.ts`, not an auth handshake) guarding against a stale/mismatched relay binary — see §5. |
| Impl | `DevServerRelayBridge.connect()` branch `connectionType === 'relay-ssh'` (`dev-server-relay-bridge.ts:140-183`); `this.session = result.transport as unknown as SshChannelMultiplexer` (cast because the SSH-deploy path's transport is structurally, not literally, the same class). |
| When used | "Phase 1"/original mode, SSH-target-bound — requires the dev server to already be a registered SSH target. |
| Agent-side note | `agent/src/relay/agent-config.ts`'s `AgentConnectionMode` type only lists `'direct-websocket' \| 'relay-websocket'` — `relay-ssh` has **no agent-local `MODE` env value**, because in this mode the "agent" binary is the SSH-deployed `relay.js`, driven entirely by the backend, not by an agent-local mode choice. |

## 4. Wire framing

### Stack A — Agent Wire Protocol v1 (`agent/src/relay/agent-wire.ts`)

13-byte header, quoted from `agent-wire.ts:4-20`:

```
Frame format (13-byte header):
  [TYPE u8][SEQ u32 BE][ACK u32 BE][LENGTH u32 BE][PAYLOAD bytes]

TYPE: MessageType.Regular (1) = JSON-RPC data frame
      MessageType.KeepAlive (9) = ping/pong frame, always empty payload

SEQ: outgoing frame sequence counter (pre-incremented before each send, starts at 1)
ACK: highest incoming SEQ seen from peer (updated by decodeFrame, sent in each outgoing frame)

export const HEADER_SIZE = 13  // 1 (type) + 4 (seq) + 4 (ack) + 4 (length)
```

`encodeFrame()` (`agent-wire.ts:53-65`) writes `type`@0 (u8), `seq`@1 (u32 BE),
`ack`@5 (u32 BE), `length`@9 (u32 BE), payload from offset 13. `decodeFrame()`
(`:80-90`) mirrors this and, as a side effect, updates `state.highestAck` if
`seq > state.highestAck`.

Constants (`agent/src/shared/agent-wire-protocol.ts:21-22`):
`AGENT_KEEPALIVE_INTERVAL_MS = 5_000`, `AGENT_TIMEOUT_MS = 20_000`.

### Stack B — Relay protocol (`protocol.ts`, byte-identical in `agent/src/relay/` and `backend/src/relay/`)

```ts
export const HEADER_LENGTH = 13
export const MAX_MESSAGE_SIZE = 16 * 1024 * 1024
export const MessageType = { Regular: 1, Handshake: 2, KeepAlive: 9 } as const
```

Same 13-byte layout via `encodeFrame(type, id, ack, payload)` (`protocol.ts:117-129`):
byte 0 = type, bytes 1-4 = id (u32 BE, plays the SEQ role), bytes 5-8 = ack (u32 BE),
bytes 9-12 = payload length (u32 BE). `KEEPALIVE_SEND_MS = 5_000`,
`TIMEOUT_MS = 20_000` (`protocol.ts:43-44`) — matching Stack A. `FrameDecoder`
(`protocol.ts:143-283`) is a chunk-list-based incremental decoder (avoids O(n²)
`Buffer.concat` re-copy per feed) that discards any frame whose declared length
exceeds `MAX_MESSAGE_SIZE` while staying byte-synchronized.

Streaming/error-code extras, Stack B only (`protocol.ts:46-86`):
`STREAM_CHUNK_SIZE = 256*1024`, `MAX_CONCURRENT_STREAMS = 16`,
`STREAM_ACK_WINDOW_CHUNKS = 4`, `GIT_RESPONSE_STREAM_THRESHOLD = 256*1024`,
`GIT_RESPONSE_CHUNK_SIZE = 128*1024`,
`RelayErrorCode = { TooManyStreams: -33006, StreamProtocolError: -33007 }`.

## 5. Handshake sequence

### Stack A — `agent.handshake` (used by both `direct-websocket` and `relay-websocket`)

Method name: `AGENT_HANDSHAKE_METHOD = 'agent.handshake'` (`agent-wire-protocol.ts:18`).

**Agent's outbound params** (`AgentHandshakeParams`, `agent-wire-protocol.ts:63-71`):

```ts
export type AgentHandshakeParams = {
  agentVersion: string
  platform: string
  arch: string
  nodeVersion?: string
  capabilities: AgentCapability[]
  agentToken?: string   // direct-websocket only
}
```

Actual constructed request (`agent-session.ts:196-214`):

```ts
{
  jsonrpc: '2.0', id: 1, method: 'agent.handshake',
  params: {
    agentVersion: '5.0.0', platform: process.platform, arch: process.arch,
    nodeVersion: process.version,
    capabilities,               // dynamically probed: git/pty availability
    ...(agentToken ? { agentToken } : {}),
    devServerId: config.devServerId,
    tools: tools.map(t => t.name)
  }
}
```

Capabilities are dynamically built (`buildCapabilities()`, `agent-session.ts:105-140`)
by probing the `git` binary and `node-pty` module load, with a 5s-timeout static
fallback (`STATIC_CAPABILITIES_FALLBACK`, lines 149-170) — includes tokens like
`fs`, `fs.watch`, `preflight`, `ai.providers`, `agent.spawn/exec/sendInput/kill`,
and conditionally `git*`, `worktrees`, `pty*`.

**Backend receiver** (`direct-websocket`, `runOrcaReceiverHandshake`,
`ws-handshake.ts:156-311`): waits `AGENT_TIMEOUT_MS` (20s) for the first frame,
requires it be `agent.handshake` (rejects/closes 1008 otherwise), validates
`agentToken` (rejects with `{error:{code: AgentErrorCode.AuthFailed (-33101), ...}}`
then `ws.close(1008, ...)`, lines 224-249), rejects agents below
`AGENT_MIN_VERSION` (`{code: AgentErrorCode.HandshakeFailed (-33100)}`, lines
251-281), then on success sends:

```ts
{ jsonrpc: '2.0', id: requestId, result: { ok: true, orcaVersion, sessionId } }
```

`sessionId = \`sess-${Date.now()}-${Math.random().toString(36).slice(2, 8)}\``.

**Agent's handling of the result** (`agent-session.ts:288-316`): if
`rpc.result?.ok === true` → `handshakeDone = true`, fires `handshakeOkCallbacks`;
if `rpc.error` → logs and `ws.close(1008, 'Handshake failed')`.

**Backend initiator** (`relay-websocket`, `runOrcaInitiatorHandshake`,
`ws-handshake.ts:56-138`): Orca sends
`{jsonrpc:'2.0', id:1, method:'agent.handshake', params:{orcaVersion}}`
(seq=1, ack=0) and waits (20s timeout) for the agent's response, parsing
`result.platform/arch/nodeVersion/agentVersion/sessionId/capabilities` into
`WsHandshakeInfo`.

Result type — `AgentHandshakeResult` (`agent-wire-protocol.ts:74-78`):
```ts
export type AgentHandshakeResult = { ok: true; orcaVersion: string; sessionId: string }
```

Both handshake functions carry an explicit fix comment about detaching the
one-shot `onMessage` listener on every settle path (`ws-handshake.ts:61-66,162-174`)
— leaving it attached previously fed every post-handshake RPC frame through
handshake-only parsing and force-closed the connection (BUG-FE-PTY-001-adjacent).

### Stack B — version handshake (`relay-ssh` only, not auth)

`relay-handshake.ts`: daemon side `setupDaemonHandshake()` (lines 83-118) reads
exactly one `MessageType.Handshake` frame before attaching the JSON-RPC dispatcher;
client (`--connect`) side `runConnectHandshake()` (lines 215-297) sends
`{type:'orca-relay-handshake', version: myVersion}` first. Message union
(`protocol.ts:20-23`):

```ts
export type HandshakeMessage =
  | { type: 'orca-relay-handshake'; version: string }
  | { type: 'orca-relay-handshake-ok'; version: string }
  | { type: 'orca-relay-handshake-mismatch'; expected: string; got: string }
```

Newer daemons append `platform`/`arch`/`nodeVersion` onto the `-ok` message
(`:188-191`) so the bridge can read them without a separate RPC call; old daemons
omit them and the client defaults gracefully (`:249-260`). Mismatch → daemon
writes `orca-relay-handshake-mismatch` and the connecting side exits with
`EXIT_CODE_VERSION_MISMATCH = 42` (`relay-handshake.ts:26,161-178,265-277`),
mapped by `ssh.ts`/`waitForSentinel` to a typed `RelayVersionMismatchError`.

## 6. The generic RPC dispatcher — bidirectional by design

`agent/src/relay/dispatcher.ts` (`RelayDispatcher`, byte-identical to
`backend/src/relay/dispatcher.ts` — see §9 caveat) is a full-duplex JSON-RPC 2.0
engine: **any** instance can both register handlers for incoming requests and
issue outgoing requests to the peer.

- **Registration API (peer → me)**:
  `onRequest(method: string, handler: MethodHandler): void` (`dispatcher.ts:148-150`),
  `MethodHandler = (params, context: RequestContext) => Promise<unknown>` (`:23-26`).
  `onNotification(method, handler: NotificationHandler): void` (`:152-154`),
  `NotificationHandler = (params, context) => void` (`:28`).
  Unhandled request methods auto-reply `{code:-32601, message:'Method not found: ...'}`
  (`:429-436`). Registration is a plain `Map.set` with **no duplicate-key
  protection** — a later registration silently overwrites an earlier one for the
  same method name (see [`gaps-and-findings.md`](./gaps-and-findings.md) for a
  concrete case where this causes a security-relevant handler override:
  `git.clone`).
- **Call API (me → peer)**:
  `requestPrimary(method, params?, {timeoutMs?})` (`:276-282`),
  `requestAnyClient(method, params?, {timeoutMs?, excludeClientId?})` (`:284-300`,
  targets any non-primary attached client — multi-tenant relay scenarios). Both
  funnel through `private requestClient(clientId, method, params?, options?)`
  (`:302-328`), default timeout `RELAY_TO_CLIENT_REQUEST_TIMEOUT_MS = 30_000`
  (`:64`). `notify(method, params?)` (`:178-190`) is fire-and-forget to all
  clients. `notifyBulk(method, params?, {clientId?})` (`:204-245`) is a
  flow-controlled bulk-lane send that awaits sink drain — used so large
  file/git-diff chunks don't head-of-line-block interactive `pty.data` frames.

On the wire actually used by the backend, `SshChannelMultiplexer.request()`
(`backend/src/main/ssh/ssh-channel-multiplexer.ts:175`) is the method the bridge
calls for outbound RPC in all 3 connection modes — a thin channel-multiplexed
wrapper over the same frame-encoded JSON-RPC request/response contract
`RelayDispatcher` implements natively. `onNotification()` (`:110`) and
`onDispose()` (`:159`) round out its bridge-facing API, and — critically —
`onRequest()` (`:145-150`) lets the **backend register a handler the agent/relay
calls**, proven concretely by `orca.cli` (see
[`backend-rpc-catalog.md`](./backend-rpc-catalog.md) §2 for the full trace and
the caveat that this is only exercised in `relay-ssh` mode today).

`RelayDispatcher` also implements per-client sequencing/reconnect bookkeeping for
relay-ssh multi-client support: `attachClient`/`detachClient`/`setWrite`
(`:96-138`) let a second SSH-socket client attach to the same relay daemon
(multi-tenant), and `invalidateClient()`/`onClientDetached()` propagate
disconnects so in-flight mutating requests are marked stale via
`context.isStale()` (`:446-451`).

## 7. Keepalive / reconnection

### Keepalive

| Layer | Interval | Owner |
|---|---|---|
| Stack A wire (both WS modes) | `AGENT_KEEPALIVE_INTERVAL_MS = 5_000` — agent sends `encodeKeepaliveFrame` (`agent-session.ts:221-227`); agent echoes backend-sent keepalives in kind (`:276-281`) | Agent-side `setInterval` in `createSession().start()` |
| `direct-websocket` WS-level ping (defends against idle-timeout proxies) | Agent sends `ws.ping()` every `KEEPALIVE_PING_MS = 20_000` after handshake-ok (`agent-connection-direct.ts:53,154-156`); backend independently pings every 30s (`agent-ws-server.ts:124-126`) | **Both sides independently** — a reverse proxy that only resets its idle timer on frames from one direction is the documented reason both ping |
| Stack B (`relay-ssh`) | `KEEPALIVE_SEND_MS = 5_000` (`protocol.ts:43`), `RelayDispatcher.startKeepalive()` (`dispatcher.ts:513-531`), `unref()`'d so it doesn't block process exit | Whichever side owns the `RelayDispatcher` instance |
| Shared idle-timeout | `AGENT_TIMEOUT_MS`/`TIMEOUT_MS = 20_000`, declared in both stacks. **Now enforced on the agent side of both stacks** (fixed — see [`gaps-and-findings.md`](./gaps-and-findings.md) #8): Stack A (`agent-session.ts`) closes the WS connection once 20s pass with no frame received; Stack B (`dispatcher.ts`) detaches an idle non-primary client after 20s (the primary SSH-channel client is only warned about, not force-closed, since its lifecycle is externally managed via `setWrite()` on reconnect). |

### Reconnection

- **`direct-websocket`**: agent owns reconnection (`agent-connection-direct.ts`,
  `runConnection()` loop lines 93-251). Backoff delays:
  `RECONNECT_DELAYS_MS = [1_000, 2_000, 5_000, 15_000, 30_000]` (line 27), capped
  at the last element thereafter. Backoff resets to 0 only if the connection
  stayed handshaked for at least `STABLE_CONNECTION_MS = 10_000` before dropping
  (lines 45,184-187) — an explicit fix for a previously-observed reconnect storm.
  On any pre-handshake close, or any post-handshake drop, the agent forces
  `tokenManager.forceRenew()` before retrying (lines 232-243), since the
  backend's token slot is single-use.
- **`relay-websocket`**: backend owns reconnection
  (`DevServerRelayBridge.connectRelayWebSocket`, `:420-551`), exponential
  backoff via `calcBackoffDelay()` (`2s * 2^attempt`, capped 60s, +0-1s jitter),
  triggered on `ws.on('close')` and on post-connect handshake failure. Reset to
  attempt 0 on successful reconnect.
- **`relay-ssh`**: no explicit reconnect loop in `DevServerRelayBridge` (the
  `relay-ssh` branch is one-shot: deploy/launch once); reconnection semantics
  live in `ssh-relay-deploy.ts`/`SshConnectionManager`. `RelayDispatcher.setWrite()`
  (`dispatcher.ts:96-105`) exists specifically to support the daemon-reconnect
  case (swapping the write callback + resetting seq/decoder state) when a new
  SSH client socket reconnects to the same still-running relay daemon.
- **Queueing during reconnect**: `DevServerRelayBridge` queues in-flight RPC
  calls for up to `RECONNECT_WAIT_MS = 20_000` while `_reconnecting` is true
  (`dev-server-relay-bridge.ts:74-77,624-716`), for both WS modes, via
  `onSessionDropped()`/`onSessionRestored()`.

## 8. Session/token lifecycle

### `AgentTokenManager` (agent side, `agent-token-manager.ts`) — `direct-websocket` only

- **Generation**: not agent-generated — fetched from backend via
  `POST /api/agent-token`. `fetchOnce()` (`:206-240`) POSTs
  `{devServerId, name, ttl, permanent: true}` with
  `Authorization: Bearer <ORCA_AGENT_API_SECRET>`, reads back `{token, expiresIn}`.
- **Default requested TTL**: `AGENT_TOKEN_DEFAULT_TTL_SEC = 86_400` (24h,
  `:32`), but the backend route can override to a 30-day permanent TTL
  server-side (see below).
- **Storage**: in-memory only (`current`/`next: FetchedToken | null`, `:63-64`)
  — never persisted to disk by the agent.
- **Rotation**: proactive renewal scheduled at `TOKEN_RENEW_RATIO = 0.8` (80%)
  of TTL (`scheduleRenewal()`, `:132-154`); the renewed token is pre-fetched and
  held as `.next` until the next WS connect calls `consume()`
  (`:95-106`), which promotes `.next → .current` and reschedules. Retry backoff
  for fetch failures: `RETRY_DELAYS_MS = [5_000, 15_000, 30_000, 60_000]` (`:35`),
  max `MAX_RENEWAL_ATTEMPTS = 5` (`:38`) — the *initial* fetch calls
  `process.exit(1)` if retries are exhausted (`:186-192`, a startup failure is
  fatal), a *later* renewal failure is not (falls back to retry-in-5-minutes
  with the current token, `:169-177`).
- **Legacy fallback**: if `ORCA_AGENT_API_SECRET` is unset, the agent falls back
  to a static `AGENT_TOKEN` env var with **no renewal** — relies on external
  process supervision (systemd) to restart with a fresh token
  (`agent-connection-direct.ts:80-88`).

### Backend `agent-token-routes.ts` — `POST/GET /api/agent-token`

- **Auth to call this endpoint**: `Authorization: Bearer <ORCA_AGENT_API_SECRET>`.
  Fail-secure: if `ORCA_AGENT_API_SECRET` is unset, the endpoint is entirely
  blocked (`isAuthorized()`, lines 38-51) — must never fall back to a
  header-bypass in production.
- **Token TTL policy** (lines 126-130): `permanent: true` in the request body →
  30-day TTL (`THIRTY_DAYS_SEC = 2_592_000`); otherwise ephemeral,
  `min(ttl, 600)` seconds (10-minute cap).
- **Token value generation**: `generateAgentToken(devServerId)`
  (`agent-wire-protocol.ts:89-91`) — format `` `agt-${devServerId}-${Date.now()}` ``.
- **Wiring**: with `DevServerManager` present, calls
  `devServerManager.connectDaemonAgent({devServerId, name, token, ttlMs})`
  (lines 137-159), which creates/updates the persisted `DevServer` record and
  wires the token into `DevServerRelayBridge.connectWithExternalToken(token)`
  (`:345-406`) — registering the slot in `AgentWebSocketServer` without
  generating a new token. Without `DevServerManager`, calls
  `agentWsServer.registerSlot(token, ...)` directly.
- **Debug listing**: in-memory `pendingMeta: Map<token, {devServerId, createdAt,
  expiresAt}>` (line 33), exposed read-only via `GET /api/agent-token` (lines
  94-108) — **plaintext tokens are returned here**, in contrast with the
  SHA-256-hashed storage inside `AgentWebSocketServer.pendingSlots`.
- **No token rotation logic lives here** — this route only mints/registers;
  renewal is entirely driven by the agent's `AgentTokenManager` re-calling this
  same endpoint.

### `relay-websocket` token (contrast)

No `AgentTokenManager`, no HTTP endpoint. `ORCA_AGENT_TOKEN` is a static,
operator-set, long-lived shared secret checked once per inbound connection by
`authenticate()` in `agent-connection-relay.ts:96-129`; never expires or rotates.

## 9. Other distinct connection types found

1. **PTY daemon Unix socket** (`agent-session.ts:33,360-370` via
   `pty-daemon-client.ts`, `agent-entry.ts:35-46` spawning itself with
   `ORCA_PTY_DAEMON_SOCKET` set to run as `runPtyDaemon`) — a **separate,
   local-only IPC channel** between the agent process and a detached
   PTY-daemon child process (not agent↔backend transport). PTYs survive
   agent-process restarts by living in this daemon instead of the agent process
   itself. NDJSON over a Unix socket (`~/orca-agent/pty-daemon.sock`), distinct
   from the 13-byte binary agent-wire framing used on the WebSocket. Not a
   backend-facing connection, but the reason `pty.*` exists twice (see
   [`agent-rpc-catalog-runtime.md`](./agent-rpc-catalog-runtime.md)).
2. **SSH exec channel for `relay-ssh`** (§3) — categorically different from the
   two WebSocket modes: no `ws` library involved at all on either side; it's
   SSH-library exec-channel stdio, wrapped by `SshChannelMultiplexer`.
3. **WSL-guest micro-relay** — a separate binary
   (`agent/src/relay/wsl-agent-hook-relay.ts`) launched inside a WSL distro by
   the Windows host, running its **own** `RelayDispatcher` instance over the
   same framed-stdio protocol (Stack B), used only for `wslfs.*` methods (a
   home-scoped filesystem bridge) and forwarding agent-hook events — see
   [`agent-rpc-catalog-runtime.md`](./agent-rpc-catalog-runtime.md).
4. **Agent-hook loopback HTTP server** — `RelayAgentHookServer`
   (`agent/src/relay/agent-hook-server.ts`), a `127.0.0.1`-only plain HTTP
   server (not JSON-RPC) that AI-agent CLIs running inside a PTY on the same
   host POST status events to; bridged into the JSON-RPC channel as an
   `agent.hook` notification. See
   [`backend-rpc-catalog.md`](./backend-rpc-catalog.md) §4.
5. **`POST/GET /api/agent-token`** (§8) — plain HTTP, not part of the JSON-RPC
   wire protocol at all, used only to mint/list `direct-websocket` tokens.
