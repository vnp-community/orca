# Frontend ↔ Backend API Surface

This directory catalogs every connection `frontend/` and `mobile/` make to a
backend process — what a from-scratch backend would need to implement for
either client to run at all. It was generated by extracting real call sites
from source (not by reading API docs, which don't exist for most of this
surface) and cross-referencing them against the backend's actual
method/route registrations.

- [`rpc-catalog.md`](./rpc-catalog.md) — every `callRuntimeRpc(...)` call site
  in `frontend/`, grouped by namespace, each checked against the backend's
  RPC method registry. **0 gaps as of 2026-08-15** — see that file's
  "Resolved gaps" section for what was fixed (the doc originally found 9;
  `gaps-and-mismatches.md`, which used to track them, has been removed since
  it no longer describes current reality).
- [`mobile-rpc-catalog.md`](./mobile-rpc-catalog.md) — the same audit for
  `mobile/`'s `sendRequest(...)`/`.subscribe(...)` call sites against the
  **same** backend RPC registry. **0 gaps as of 2026-08-27** (144 methods).
  Mobile has no backend of its own — it pairs directly with the desktop app's
  `OrcaRuntimeRpcServer` over an E2EE WebSocket; see that file's architecture
  section for how pairing/transport differs from the frontend's Electron
  IPC/environment-target routing, and which namespaces (`ui`, `settings`,
  `session.tabs`, `speech`, `clipboard`, `aiVault`, `markdown`, `stats`) are
  called directly as RPC from mobile with no desktop-local equivalent.
- [`http-endpoints.md`](./http-endpoints.md) — plain HTTP (`fetch`) calls: auth,
  the admin console's REST API, web push. Frontend (desktop/web) only — mobile
  has no plain-HTTP backend surface (see `mobile-rpc-catalog.md`'s
  architecture note; even push-notification subscription goes over RPC).
- [`ipc-surface.md`](./ipc-surface.md) — `window.api.*` (Electron `contextBridge`
  preload), the same-process renderer↔main-process channel. As of 2026-08-15
  this also documents a deliberate scope narrowing: most namespaces that used
  to be pure indirection over an RPC call on the web build (`gh`, `gl`,
  `repos`, `worktrees`, parts of `fs`/`ssh`, `credentials`) now call the RPC
  layer directly instead. What's left on `window.api.*` is the RPC transport
  itself plus genuinely desktop/OS-only work (`ui`/`settings`/`pty`/`shell`/
  native dialogs/OS keychain/etc.) — see that file for the full breakdown of
  what was and wasn't migrated, and why.
- [`backend-agent-execution-boundary.md`](./backend-agent-execution-boundary.md) —
  for every RPC method, does the **backend** process it itself
  (PostgreSQL-backed) or **relay to the Dev Server Agent** (`agent/`,
  running on a remote SSH-connected dev server)? Most of the largest
  namespaces (`git.*`, `files.*`, `worktree.*`, `terminal.*`) don't have a
  static answer — the same method dispatches either way per call, based on
  which host owns the target worktree. Also documents where GitHub/GitLab
  still self-execute on backend instead of relaying (a known drift from the
  HLD's Control-Plane/Data-Plane design), the "one JSON blob" Postgres
  storage model, and several real bugs/gaps found while tracing the dispatch
  logic (not guessed — code-grounded, file:line cited).

## Connection types

Orca's frontend talks to a "backend" over three genuinely different channels,
which this doc set treats separately. `mobile/` only ever uses the first —
see [`mobile-rpc-catalog.md`](./mobile-rpc-catalog.md) for how its transport
(E2EE-paired WebSocket to the desktop app) differs from channel 1 below even
though the wire protocol and method registry are identical:

1. **Runtime RPC over WebSocket** (`callRuntimeRpc()`,
   `frontend/src/renderer/src/runtime/runtime-rpc-client.ts`) — a JSON-RPC-style
   protocol (`{id, method, params, authToken}` request / `{id, ok, result|error}`
   response) carried over a WebSocket, dispatched server-side by
   `OrcaRuntimeRpcServer` (`backend/src/main/runtime/runtime-rpc.ts`) against a
   method registry built from `defineMethod()`/`defineStreamingMethod()` calls
   spread across `backend/src/main/runtime/rpc/methods/*.ts` and a handful of
   feature-owned files (`project/project-rpc-handler.ts`,
   `team/team-rpc-handler.ts`, `workflow/workflow-rpc-handler.ts`, …). This is
   the primary, largest surface — **262 distinct methods** called from
   frontend files as of 2026-08-15, all 262 confirmed on the backend — and the
   one this doc set covers in full detail in `rpc-catalog.md`. As of this
   update it's also the *only* channel most non-desktop-only operations use:
   see (3) below for what changed.
2. **Plain HTTP** (`fetch()`) — session auth (`/auth/*`), the admin console's
   REST API (`/admin/api/*`, via `admin-api-client.ts`'s `adminFetch()`), and web
   push subscription (`/api/push-*`). Covered in `http-endpoints.md`.
3. **Electron IPC** (`window.api.*`, same OS process — renderer to main, not a
   network call) — covered in `ipc-surface.md`. Still out of primary scope for
   the same structural reason (in Electron the "main process" IS the
   frontend's own app process, not a separate server), but as of 2026-08-15
   it's narrower than it used to be: most namespaces that were pure
   indirection over an RPC call on the web build now call `callRuntimeRpc()`
   directly via `renderer/src/runtime/runtime-*-client.ts` wrapper files
   instead of routing through the `window.api.*` → `web-preload-api.ts` shim
   → RPC chain. What's left on `window.api.*` is the RPC transport itself
   (`window.api.runtime`/`runtimeEnvironments`, load-bearing, not removable)
   plus genuinely desktop/OS-only work with no backend equivalent — see
   `ipc-surface.md` for the full namespace-by-namespace breakdown.

## Methodology

- **Backend registry**: `grep -rhoE "name: '[a-zA-Z][a-zA-Z0-9]*\.[a-zA-Z0-9_.]+'"`
  across `backend/src/main/` (every `defineMethod`/`defineStreamingMethod` call
  site sets a literal `name: '...'` string) → 583 unique method names as of
  2026-08-15 (was 578; +5 for `annotation.create/list`, `fleet.health.checkAll`,
  `ssh.getUserAccount`, `workflow.template.update`).
- **Frontend call sites**: every file importing `callRuntimeRpc`, scanned for
  `callRuntimeRpc(<target>, '<method>', ...)` call expressions (multiline-aware)
  → 262 unique method names, all 262 confirmed on the backend, as of 2026-08-15.
- **Cross-reference**: a frontend method name not present verbatim in the
  backend registry would be flagged `❌ missing` in `rpc-catalog.md` — as of
  this update, none are (`rpc-catalog.md`'s "Resolved gaps" section covers
  what the 9 previous gaps were and how each was fixed).
- This is a **static, name-level** check — it confirms a method exists, not that
  its parameter shape matches (BUG-FE-RPC-004/005, fixed earlier in this
  session's history, were both cases where the method name matched but the
  params/response shape didn't — that class of bug is invisible to this
  methodology and needs a runtime/schema-level check instead).
- Backend methods with **no** frontend `callRuntimeRpc` caller at all (≈320 of
  the 583) aren't enumerated individually — they're either desktop-only entry
  points reached via `window.api.*` → Electron IPC → the same dispatcher (not
  captured by this grep), CLI-only (`backend/src/cli`), or genuinely unused from
  this frontend. Worth a follow-up pass if that reverse direction matters.
- Re-run: `grep -rhoE "name: '[a-zA-Z][a-zA-Z0-9]*\.[a-zA-Z0-9_.]+'" --include="*.ts" backend/src/main/ | sed "s/name: '//;s/'//" | sort -u`
  for the backend side; see `rpc-catalog.md`'s intro for the frontend-side
  perl one-liner. `comm -23 <frontend-sorted> <backend-sorted>` gives the gap
  list directly.
