# Backend ↔ Dev Server Agent Execution Boundary

For every RPC method in [`rpc-catalog.md`](./rpc-catalog.md): does the backend
process the call itself (PostgreSQL-backed), or does it relay to the Dev
Server Agent (`agent/`) running on a remote SSH-connected dev server? This
was generated by tracing every namespace's RPC handlers into their real
implementation (not inferred from naming or the HLD's intended design) —
methodology and caveats in the last section.

## The single most important fact: most of this is decided per-call, not per-method

For the largest namespaces (`git.*`, `files.*`, `worktree.*`, most of
`terminal.*`), there is **no static answer** to "does this method use
Postgres or the Agent?" — the same RPC method does either, decided at call
time by which host owns the target worktree:

```ts
// The pattern repeated ~30+ times across orca-runtime-git.ts,
// orca-runtime-files.ts, orca-runtime-worktree-*.ts:
const target = await this.host.resolveRuntimeGitTarget(worktreeSelector)
const provider = target.connectionId ? getRemoteGitProvider(target.connectionId) : null
if (target.connectionId) {
  // relay: provider.<method>() → Dev Server Agent (or SSH target)
} else {
  // local: backend executes git/fs directly, no agent involved
}
```

`connectionId` comes from `getRepoProviderConnectionKey(repo)` — the repo's
`connectionId` (raw SSH target) or `devServerId` (Dev Server Agent), or
`undefined` for a purely local repo. So "which namespaces relay to the
agent" is really "which namespaces are worktree/host-scoped" — those *can*
relay, on a request-by-request basis, while namespaces with no host concept
(profile, project, team, task metadata, workflow templates, most
integrations) never do.

## Three distinct relay mechanisms — don't conflate them

Despite all being "connectionId-keyed," these are three separate transports:

| Mechanism | Used by | Registry | Agent-side |
|---|---|---|---|
| **Dev Server Agent WS-RPC relay** | `git.*`, `files.*`, `worktree.*`, `terminal.*` (PTY), `devServer.browseDir/mkdir/rmdir` | `getRemoteGitProvider`/`getRemoteFilesystemProvider`/`ptyConnectionProviders` (`backend/src/main/providers/*-dispatch.ts`) → `DevServerGitProvider`/`DevServerFilesystemProvider`/`DevServerPtyProvider` | `agent/src/relay/agent-rpc-dispatch.ts`'s `git.*`/`fs.*`/`pty.*` cases |
| **SSH session multiplexer** | `preflight.detectRemoteAgents`, `preflight.detectRemoteWindowsTerminalCapabilities`, raw SSH-target PTYs (`SshPtyProvider`), raw SSH-target git (`SshGitProvider`) | `getActiveMultiplexer(connectionId)` | The relay binary deployed via `ssh.bootstrapServer`, a different wire protocol than the WS relay |
| **SFTP filesystem provider** | `clipboard.saveImageAsTempFile`/`commitImageUpload` | Same `providers/ssh-filesystem-dispatch.ts` registry as the WS relay, but calls raw SFTP (`provider.writeFileBase64`), not a `fs.*` RPC method | N/A — plain SFTP, not an agent RPC call |

A worktree can be backed by either an **SSH target** (raw `ssh2` connection,
handled by `SshGitProvider`/`SshPtyProvider`, talking to a relay binary
deployed by `ssh.bootstrapServer`) or a **Dev Server Agent** (a persistent
WS connection registered via `devServer.connect`, handled by
`DevServerGitProvider`/`DevServerFilesystemProvider`/`DevServerPtyProvider`).
Both register into the *same* `connectionId`-keyed provider maps, so
backend's dispatch code treats them uniformly — but **the two providers'
method coverage is not identical** (see Known Gaps below).

## Postgres storage model: one JSON blob, not per-entity tables

With one confirmed exception (orchestration), **nothing in this codebase
does per-row Postgres CRUD for runtime state**. `Store` (`backend/src/main/
persistence.ts`) holds the *entire* application state — worktree metadata,
SSH targets, dev servers, port forwards, UI/client settings, project
groups, folder workspaces, automations config — as one JSON document,
hydrated once at boot (`Store.hydrateFromPostgres()`) and persisted back on
mutation via `PgOrcaDataStatePersistence.save()`
(`backend/src/main/persistence/orca-data-state-persistence.ts`) against a
**single table**, `core.orca_data_state_blob`, keyed by `(tenant_id,
user_id)`. So "Postgres involvement: yes" below almost always means "goes
through this one blob," not a dedicated SQL table — except:

- **`orca_ai_provider_accounts`**, **`orca_provider_usage`**, **`orca_annotations`**,
  **`orca_v5_projects`**, **`orca_v5_project_members`**, **`orca_teams`**,
  **`orca_team_members`**, **`orca_tasks`**, **`orca_task_edges`**,
  **`orca_task_comments`**, **`orca_task_grants`**, **`orca_workflow_templates`**,
  **`orca_workflow_executions`**, **`orca_workflow_step_executions`**,
  **`orca_companies`**, **`orca_departments`**, **`orca_user_profiles`** — genuine
  per-entity relational tables (v5.0 "collaborative" domains: profile,
  project, team, task, workflow).
- **`PgOrchestrationDb`** (`backend/src/main/runtime/orchestration/pg-db.ts`,
  `orca_orchestration_*` tables, migration 0020) — genuinely relational,
  used by `task.execute`'s complex-task path and `worktree.lineageList`'s
  lineage inference.
- **`PgAutomationStore`** — automations are Postgres-backed via a
  dedicated store, not the blob.
- **`PgWebPushStore`** — mobile push subscriptions, reached only
  indirectly (see `notifications.*` below).

Everything else that says "Postgres: yes" in the tables below means "the
one JSON blob," which matters for anyone reasoning about migration/scaling —
it's not a normalized schema for worktrees, SSH targets, or dev servers.

## Namespace-by-namespace classification

Legend: 🔀 dynamic (per-call, decided by `connectionId`) · 🟢 always
backend+Postgres · 🏠 always backend-local (no DB, no relay) · 🔌 always
relays (no local path exists) · ⚠️ known bug/gap

### Worktree/host-scoped — can relay to the Dev Server Agent per call

| Namespace | Dispatch | Notes |
|---|---|---|
| `git.*` (34 methods) | 🔀 | Every method identical pattern. 8 methods (`checkIgnored`, `submoduleStatus`, `history`, `branchCompare`, `commitCompare`, `branchDiff`, `commitDiff`, `forkSync`) map to **dedicated** agent RPC methods; the rest compose from the agent's generic `git.exec` passthrough. Zero Postgres involvement in the git chain itself (only reads the already-hydrated `Store`, never writes). ⚠️ `generateCommitMessage`/`generatePullRequestFields`/`discoverCommitMessageModels` call `provider.executeCommitMessagePlan!()` with a non-null assertion — `DevServerGitProvider` does **not** implement this (only `SshGitProvider` does), so these 3 methods throw a raw `TypeError` for Dev-Server-backed (not SSH-backed) repos, despite `dev-server-git-provider.ts`'s own header comment claiming full coverage. `cancelGenerateCommitMessage`/`cancelGeneratePullRequestFields` avoid the crash via optional chaining. |
| `files.*` (~20 methods) | 🔀 | Same pattern via `getRemoteFilesystemProvider`. ⚠️ The agent's filesystem surface is **narrower** than backend's API: `files.rename`, `files.copy`, `files.commitUpload` all fail (`NOT_SUPPORTED`) for Dev-Server-backed repos — `DevServerFilesystemProvider` only implements `stat/readDir/readFile/writeFile/mkdir/rmdir/glob/grep`, not `rename/copy/realpath`. `files.readChunk` is unsupported for *any* remote target (SSH or Dev Server) by design. `files.open`/`openDiff`/`unwatch`/`browseServerDir` are always-local (no fs I/O, just renderer notification/bookkeeping). No Postgres in the hot path. |
| `worktree.*` (15 methods) | 🔀 (mostly) | Uses the *same* `getRemoteGitProvider` registry as `git.*` — worktree creation/removal/listing are git operations. `worktree.set`, `persistSortOrder`, `forgetLocal` are 🏠 always-local (never relay; `forgetLocal` exists specifically as an escape hatch for worktrees whose remote provider is gone). ⚠️ `worktree.forceDeleteBranch` has the identical crash pattern to the git.ts bug above: `provider.forceDeletePreservedBranch!()` isn't implemented by `DevServerGitProvider`. All mutating methods write worktree metadata/lineage to the Postgres blob; `worktree.lineageList` additionally reads the genuinely-relational `PgOrchestrationDb`. |
| `terminal.*` (~25 methods) | 🔀 (Electron) / 🔌 (server) | In **desktop/Electron** deployment: `connectionId` unset → real local `node-pty`; set → `SshPtyProvider`/`DevServerPtyProvider`. In the **pure-Node multi-user server** deployment, there is no local-shell path at all — `server-pty-controller.ts` throws immediately if `connectionId` is missing ("no local shell" by design). Two separate agent-side PTY transports exist: Dev Server Agent connections talk to a **detached daemon process** (`pty-daemon-client/server.ts`, the "session survives agent restart" fix machinery — see your memory notes on the pane-remount bug); raw SSH targets talk to a differently-named relay protocol (`pty.spawn` vs `pty.create`, etc.) via `ssh-pty-provider.ts`. No Postgres for PTY I/O itself. |
| `preflight.check` | 🔀 | Relays via `ctx.devServerManager.getRelay(devServerId)` — the WS relay, same transport as git/files. `preflight.detectAgents`/`refreshAgents` are 🏠 always-local. **`preflight.detectRemoteAgents`/`detectRemoteWindowsTerminalCapabilities` use the *different* SSH-multiplexer transport** (`getActiveMultiplexer`), not the WS relay — easy to miss if you only read the WS-relay code path. |
| `devServer.browseDir`/`mkdir`/`rmdir` | 🔌 always relay | No local path is meaningful (browsing a *remote* server's filesystem). Plain `fs.readDir`/`fs.mkdir`/`fs.rmdir` on the agent. |
| `devServer.list`/`add`/`remove` | 🟢 always backend+Postgres | CRUD against the blob via `DevServerStore`. `remove` additionally tears down a live relay connection as a side effect. |
| `devServer.connect`/`disconnect`/`testConnection` | 🔌 always relay | Establishes/tests the actual agent connection; **connection status is explicitly not persisted** (runtime-only). |
| `devServer.listSshTargets`/`addSshTarget` | 🟢 (intended) | ⚠️ **Likely broken**: constructs `new SshConnectionStore()` with no arguments, but the constructor requires a `Store` param with no default (every other call site passes one) — this looks unreachable/crashing as written. |
| `ssh.getState`/`listTargets`/`listRemovedTargetLabels`/`listProjects`/`listTeams`/`filterTargets`/`getAllConnectionStates`/`listPortForwards`/`listDetectedPorts`/`getFleetStatus`/`getUptimeHistory`/`getUserAccount`/`needsPassphrasePrompt` | 🏠 always-local | Pure in-memory reads (`SshConnectionStore`/`connectionManager`/`fleetHealthStore`), backed by the Postgres blob for the persisted parts (targets), but no relay ever. `getUptimeHistory` is pure in-memory, no persistence at all. |
| `ssh.connect`/`disconnect` | 🔌 always remote | *Is* the connection-establishment act itself. |
| `ssh.addPortForward`/`updatePortForward`/`removePortForward` | 🔌 always remote-dependent | Tunnels a local socket through an already-live SSH channel; config persisted to the blob. |
| `ssh.bootstrapServer` | 🔌 always remote | Installs Node/git and deploys the relay binary over the raw SSH connection — this is what makes an SSH target *become* relay-capable in the first place. |
| `ssh.importFleetConfig` | 🏠 always-local | Reads a local YAML file on the backend host; writes targets to the Postgres blob. |
| `clipboard.saveImageAsTempFile`/`commitImageUpload` | 🔀 (SFTP, not WS relay) | Only `clipboard.*` method with any host-branching — via a raw SFTP `IFilesystemProvider`, not the Dev Server Agent RPC surface. Other `clipboard.*` methods (`startImageUpload`/`appendImageUploadChunk`/`abortImageUpload`) are 🏠 in-memory chunk buffering only. |
| `workspacePorts.scan`/`kill` | 🏠 always-local | ⚠️ **Silently excludes remote-connected repos** rather than relaying or erroring — any worktree whose repo has a `connectionId` is filtered out before scanning, so scanning a Dev-Server-hosted repo just returns an empty port list. |

### GitHub/GitLab/integrations — backend self-executes (documented drift), with one recent partial fix

| Namespace | Dispatch | Notes |
|---|---|---|
| `github.*` (46 methods, except auth) | 🏠 backend self-executes | Runs `gh` CLI via `child_process.execFile` **in the backend process**, using the backend host's shared OS keychain — **not** relayed to the Dev Server Agent, contradicting the HLD's Control-Plane/Data-Plane design. `⚠️` As of commit `c88c918fa`, a hard guard (`assertLocalGhCliAllowed()`) now throws `MULTI_USER_GH_CLI_NOT_SUPPORTED` when `ORCA_MULTI_USER=1` — this fails safe (blocks the feature) rather than fixing the underlying design gap (relay to Agent). `⚠️` **Security gap**: `github.checkOrcaStarred`/`github.starOrca` call the CLI through a *legacy* code path that bypasses this guard entirely — they'd still self-execute with shared credentials even in multi-user mode. |
| `gitlab.*` (18 methods, except auth) | 🏠 backend self-executes | Identical pattern via `glab` CLI, same multi-user guard applies uniformly (no bypass found here). |
| **`github.startAuthLogin`/`revokeAuth`, `gitlab.startAuthLogin`/`revokeAuth`** | 🔌 **relays to Dev Server Agent** | **Correction to the drift above**: these 4 methods genuinely relay via `getRemotePtyProvider(devServerId).spawn()`, running `gh auth login`/`glab auth login` on the dev server with per-user `GH_CONFIG_DIR`/`GLAB_CONFIG_DIR` isolation (recent fix, commit `c88c918fa`). The rest of `github.*`/`gitlab.*` still self-executes on backend — auth is the one exception. |
| `hosted-review.*` (3 methods) | 🏠 mixed | GitHub/GitLab-branch reviews go through the same self-executed CLI path; Bitbucket/Azure DevOps/Gitea go through per-user HTTP clients using `WebCredentialStore` tokens. `pr_created` stats write to a local JSON file (`orca-stats.json`), not Postgres. |
| `jira.*` (18 methods), `linear.*` (22 methods), `linear-agent-access.*` (13 methods) | 🏠 backend-local, no CLI/agent | HTTPS REST (Jira) / GraphQL SDK (Linear) calls directly from backend. Credentials in per-service encrypted files (`~/.orca/jira-*`, `~/.orca/linear-*`, Electron `safeStorage`) or `WebCredentialStore` in multi-user mode — **not Postgres**. One side effect: `linear.resolveCurrentIssue` writes `linkedLinearIssueWorkspaceId` onto the worktree's blob row. |

| Namespace | Dispatch | Notes |
|---|---|---|
| `profile.*` (11 methods) | 🟢 | `orca_companies`/`orca_departments`/`orca_user_profiles`/`orca_users` (relational tables). No relay anywhere. |
| `project.*` (10 methods) | 🟢, except one | `orca_v5_projects`/`orca_v5_project_members`. ⚠️ **`project.agentSpawn`** is the exception — despite living in this namespace, it delegates entirely to `ProfileAwareAgentSpawner.spawn()` → `relay.call('agent.exec', ...)`. No project row is touched by the spawn itself. |
| `team.*` (5 methods) | 🟢 | `orca_teams`/`orca_team_members`. |
| `task.*` | 🟢, except two | `orca_tasks`/`orca_task_edges`/`orca_task_comments`/`orca_task_grants` for CRUD/grants. ⚠️ **`task.aiDecompose`** relays via `relay.call('ai.complete', {prompt, format:'json', ...})` — AI inference runs on the Dev Server Agent, not in-process (easy to miss since the method mostly *looks* like a DB read). ⚠️ **`task.execute`** branches by complexity: simple tasks relay through the same `agent.exec` path as `project.agentSpawn`; complex tasks (with subtasks/dependencies) hand off to `TaskOrchestrationBridge` → the relational `PgOrchestrationDb`, and the coordinator's worker dispatch also eventually reaches the Dev Server Agent. |
| `workflow.*` | 🟢 for the RPC call itself; steps relay | `orca_workflow_templates`/`orca_workflow_executions`/`orca_workflow_step_executions`. `workflow.execute` returns immediately (DB-only), but the async execution's step types split: `agent`/`shell`/`notification` steps relay to the Dev Server Agent (`relay.call('agent.exec'|'shell.exec'|'notification.send', ...)`); `webhook` runs a native `fetch()` on backend; `condition` is a pure in-memory expression evaluator. Per-step status is always written to Postgres regardless of where the step ran. |
| `automation.*` | 🟢, execution stubbed | CRUD/list/precheck via `PgAutomationStore` (Postgres) — the same `AutomationService` class desktop uses, not a reimplementation. ⚠️ **`automation.runNow`/scheduled dispatch has no working execution path on backend today** — the dispatcher is intentionally left `undefined` server-side (explicit TODO in `server-bootstrap.ts`), so due/triggered runs fall back to `skipped_unavailable` instead of relaying anywhere. Genuinely unimplemented, not a relay. |
| `orchestration.*`/`orchestration-gates.*` | 🟢 relational | Entirely against `PgOrchestrationDb` (message bus, task queue, gates, coordinator state). One side effect (`sendTerminalAgentPrompt`) reaches into the terminal/PTY layer, where relay may occur — not this namespace's own logic. |
| `folderWorkspace.*`, `projectGroup.*` | 🟢, local-FS assist | CRUD via the Postgres blob (`store.createFolderWorkspace`/`createProjectGroup`). `projectGroup.scanNested`/`importNested` do a local filesystem directory scan on the backend host first, then persist results — no relay. |
| `settings.*`/`ui.*` (`client-ui.ts`) | 🟢 | Backend client-settings/UI-state, through the Postgres blob. |

## Known bugs/gaps surfaced by this investigation (not fixed, flagged for follow-up)

1. **Security**: `github.checkOrcaStarred`/`github.starOrca` bypass the multi-user `gh` CLI guard entirely (legacy code path) — would still run with shared credentials under `ORCA_MULTI_USER=1`.
2. **Crash risk (pattern, 2 instances)**: `DevServerGitProvider` doesn't implement `executeCommitMessagePlan`/`cancelGenerateCommitMessage`'s counterpart or `forceDeletePreservedBranch`, both optional on `IGitProvider` and implemented only by `SshGitProvider`. Callers use non-null assertions (`provider.x!()`), so `git.generateCommitMessage`/`generatePullRequestFields`/`discoverCommitMessageModels` and `worktree.forceDeleteBranch` throw raw `TypeError`s for Dev-Server-backed (not SSH-backed) repos.
3. **Likely broken/unreachable**: `devServer.listSshTargets`/`addSshTarget` construct `SshConnectionStore` with no constructor argument, but the constructor requires one with no default.
4. **Unimplemented (not a relay, not a bug — a real gap)**: `automation.runNow`/scheduled dispatch has no execution path on the backend server deployment; runs always resolve `skipped_unavailable`.
5. **Silent capability gap**: `workspacePorts.scan`/`kill` silently return empty results for remote-connected repos instead of relaying or erroring.
6. **Stale audit correction**: the earlier finding "only `preflight.check` relays to the Dev Server Agent, all GitHub/GitLab operations self-execute" is now only *partially* true — `github.startAuthLogin`/`revokeAuth`/`gitlab.startAuthLogin`/`revokeAuth` relay as of a recent fix; the other 60+ GitHub/GitLab methods still self-execute.

## Methodology

Generated by 5 parallel investigation passes over every file in
`backend/src/main/runtime/rpc/methods/*.ts` plus `project/project-rpc-handler.ts`,
`team/team-rpc-handler.ts`, `workflow/workflow-rpc-handler.ts`,
`profile/profile-rpc-handler.ts`, and `ai-providers/ai-provider-rpc-handler.ts` —
each method's RPC definition traced into its real implementation (the
`OrcaRuntimeService`/`RuntimeXCommands` classes and underlying service
modules), not inferred from the HLD's intended design or namespace naming.
Every dispatch claim above is code-grounded (file:line citations exist in
the source investigation, condensed here for readability) rather than
assumed uniform across a namespace — several namespaces turned out to mix
dispatch behavior per-method (`aiProvider.*`, `hosted-review.*`) or even
per-branch within one method (`hosted-review.create`). Cross-referenced
against the Dev Server Agent's real RPC surface
(`agent/src/relay/agent-rpc-dispatch.ts`) to confirm which backend-side
relay calls have a genuine agent-side handler.

This is current as of 2026-08-15. Re-verify before relying on it for a
security-sensitive decision — several of the "drift" findings above (e.g.
GitHub/GitLab auth relaying) were themselves recent fixes that changed the
picture from an audit written just one week earlier.
